# Home Presence Telegram Bot

Асинхронний бот для домашньої мережі на Linux Mint 22.3. NetAlertX виявляє пристрої через ARP, бот обліковує присутність за MAC, зберігає історію в SQLite та надсилає повідомлення через Telegram. Два основні телефони можна додати через меню, а мережеві налаштування вводяться під час розгортання. Час у боті показано в `Europe/Kyiv`.

## 1. Підготовка HP ProBook

Скопіюйте проєкт на HP. Виконайте команди в його Linux-терміналі.

```bash
ip -4 -br addr
ip -4 route
ip neigh
sudo ss -lntup '( sport = :20211 or sport = :20212 )'
docker ps --format 'table {{.Names}}\t{{.Ports}}'
ip link show br-homepresence
```

- Знайдіть інтерфейс HP і CIDR домашньої мережі. Наприклад, `192.168.0.0/24 --interface=enp0s25`. Для ARP телефони та HP мають бути в одному сегменті L2. Ethernet до Tenda бажаний, якщо доступний.
- Виберіть контрольну MAC пристрою, що постійно відповідає на ARP в цьому сегменті. Зазвичай це LAN-адреса шлюзу Tenda з `ip neigh`. Уникайте MAC самого HP, синтетичного запису `Internet` та сплячих клієнтів.
- Якщо порт уже зайнятий NetAlertX, використайте його наявний екземпляр після перевірки сумісності й налаштувань сканування. Для конфлікту з іншим сервісом виберіть вільні порти. Вкажіть їх у `NETALERTX_WEB_PORT`, `NETALERTX_API_PORT` і, для API, також у `NETALERTX_URL`. Якщо назву `br-homepresence` уже використовує стороння мережа, виберіть унікальну назву в Compose та використовуйте її у правилах доступу нижче.
- Переконайтеся, що сервер не переходить у сон при закритій кришці або через бездіяльність і синхронізує час. Перевірте це через налаштування живлення Mint і `timedatectl`.

## 2. Налаштування NetAlertX

Проєкт звірено з релізом **26.10.28**. Окремий Compose використовує підтверджений тег `ghcr.io/netalertx/netalertx:26.10.28`. У ньому є host networking, вбудований healthcheck NetAlertX та той самий набір capabilities, що й у захищеному Compose релізу. Три мережеві capabilities потрібні образу та сканерам, а `CHOWN`, `SETUID` і `SETGID` дозволяють підготувати том і перейти на непривілейованого користувача. [Офіційний Compose цього релізу](https://github.com/netalertx/NetAlertX/blob/v26.10.28/docker-compose.yml) · [Інструкція Docker](https://docs.netalertx.com/DOCKER_INSTALLATION/)

### Доступ до API

NetAlertX прив’язує API до `0.0.0.0`. Для нового екземпляра вебінтерфейс у Compose прив’язано до `127.0.0.1`, API слід обмежити на хості. Перед запуском переконайтеся, що Tenda не перенаправляє ці порти й вони не відкриті через DMZ, UPnP, публічний тунель або проксі. Обмежте вхід до API з домашньої мережі за допомогою наявного хостового файрвола. [Прив’язка API](https://docs.netalertx.com/API/) · [Мережі Docker Compose](https://docs.docker.com/compose/how-tos/networking/)

Ось приклад для сервера з активним UFW. Після перевірки конфліктів підставте фактичний API-порт. Два правила застосовуються в порядку від першого до другого.

```bash
sudo ufw status numbered
sudo ufw insert 1 allow in on br-homepresence to any port 20212 proto tcp
sudo ufw insert 2 deny in to any port 20212 proto tcp
```

Правила UFW застосовуйте лише якщо UFW вже активний. Для хоста з nftables можна додати окрему таблицю до чинного набору правил через штатний механізм його збереження. Приклад обмежує лише вхід до вказаного API-порту для IPv4 та IPv6.

```nft
table inet home_presence {
    chain input {
        type filter hook input priority -10; policy accept;
        iifname != { "lo", "br-homepresence" } tcp dport 20212 drop
    }
}
```

Збережіть приклад у файл, перевірте його командою `sudo nft -c -f файл` і завантажте через `sudo nft -f файл`. Для збереження після перезапуску включіть цей файл у конфігурацію вашого хостового файрвола. Якщо чинний файрвол має політику drop, окремо дозвольте доступ для `br-homepresence` в його правилах. Для наявного NetAlertX врахуйте поточних клієнтів перед внесенням правил. Бот працює без публікації портів. [Вхідні ланцюги nftables](https://wiki.nftables.org/wiki-nftables/index.php/Configuring_chains)

### Новий екземпляр

1. Створіть локальний файл конфігурації з правами читання лише для користувача.

   ```bash
   umask 077
   cp .env.example .env
   chmod 600 .env
   ```

2. Виконайте з термінала або розгорніть окремий стек `home-presence-netalertx` у Portainer за інструкцією нижче.

   ```bash
   docker compose -p home-presence-netalertx -f docker-compose.netalertx.yml config --quiet
   docker compose -p home-presence-netalertx -f docker-compose.netalertx.yml up -d
   ```

3. Відкрийте на HP `http://127.0.0.1:20211`. З іншого комп’ютера можна скористатися SSH-тунелем `ssh -L 20211:127.0.0.1:20211 користувач@IP_HP`, якщо SSH на HP уже налаштовано.
4. У NetAlertX у **Settings** укажіть `SCAN_SUBNETS` для однієї домашньої підмережі. Якщо параметри ARPSCAN приховані, додайте `ARPSCAN` до **Loaded plugins**. Виставте `ARPSCAN_RUN = schedule` і `ARPSCAN_RUN_SCHD = * * * * *` для запуску щохвилини. Збережіть зміни. Для цієї конфігурації використовуйте ARPSCAN як єдине джерело присутності, щоб сторонній сканер або імпорт DHCP не оновлював контрольну мітку в проміжному циклі. Плагіни збагачення назв можна залишити, якщо вони не оновлюють присутність. [Налаштування підмереж](https://docs.netalertx.com/SUBNETS/) · [Плагін ARPSCAN](https://docs.netalertx.com/plugins/arp_scan/) · [Розклад релізу](https://github.com/netalertx/NetAlertX/blob/v26.10.28/server/plugins/arp_scan/config.json)
5. Дочекайтеся двох сканів. Переконайтеся, що контрольна MAC та обидва телефони є в списку. Для контролю та телефонів у NetAlertX має бути ввімкнено сканування, вимкнено примусовий статус і архівацію. Використовуйте самостійні записи пристроїв без об’єднання телефонів у NIC-пари.
6. У **Settings → General** скопіюйте значення `API_TOKEN` до `.env` бота. Збережіть згенерований NetAlertX токен або задайте свій у UI. Передавання токена через `APP_CONF_OVERRIDE` тут опущено, бо реліз може логувати значення override на рівні verbose. Під час роботи з токеном використовуйте локальний UI або SSH-тунель. [Авторизація](https://docs.netalertx.com/API/) · [Обробка override в релізі](https://github.com/netalertx/NetAlertX/blob/v26.10.28/server/initialise.py)

Якщо NetAlertX уже встановлено, використайте його API й токен. Спочатку перевірте контракт розділу нижче. Для розкладу раз на 5 хвилин задайте в боті `SCAN_SECONDS=300` та врахуйте більшу затримку підтвердження. Фактичний розклад на HP потрібно звірити за `/status` після 2–3 циклів.

## 3. Налаштування й запуск бота

1. Створіть окремого бота через офіційний `@BotFather` і запишіть токен у `TELEGRAM_BOT_TOKEN`. Для цієї конфігурації потрібен long polling. Для одного токена запускайте одну копію контейнера.
2. Заповніть у `.env` `ADMIN_USER_IDS`, `MEMBER_USER_IDS`, `REFERENCE_MAC` і `API_TOKEN`. Для кількох ID використовуйте кому. Приватний chat ID дорівнює числовому user ID. Кожен одержувач у приватному чаті має відкрити бота й надіслати `/start`.
3. Для спільної групи додайте до неї бота й надішліть команду з адресацією `/start@НазваВашогоБота`. Команда нижче покаже chat ID групи, він від’ємний. Додайте його у `ALLOWED_GROUP_IDS` до запуску або під час наступного розгортання. Режим приватності групи можна залишити ввімкненим, оскільки форми приймають відповіді на повідомлення бота. [Отримання оновлень Telegram](https://core.telegram.org/bots/api#getting-updates) · [Режим приватності](https://core.telegram.org/bots/features#privacy-mode)
4. За потреби задайте `ADMIN_CHAT_ID`, `DISCOVERY_CHAT_ID`, `GUEST_CHAT_ID` у `.env` або через `/settings`. За замовчуванням використовується приватний чат адміністратора з найменшим ID, а нові MAC та візити гостей ідуть за тим самим маршрутом. Усі одержувачі мають бути у відповідному списку дозволених ID. Спільна група показуватиме сповіщення всім учасникам цієї групи.

Якщо потрібен числовий user ID або chat ID, використайте `getUpdates` до запуску стека. Спершу надішліть боту `/start` у приватному чаті або групі. Якщо стек уже працює, тимчасово зупиніть його на час перевірки. Команда друкує лише ID авторів і чатів.

```bash
docker build -t home-presence-bot:1 .
docker run --rm --env-file .env home-presence-bot:1 python -c '
import asyncio, os
from aiogram import Bot
async def run():
    async with Bot(os.environ["TELEGRAM_BOT_TOKEN"]) as bot:
        for update in await bot.get_updates(allowed_updates=["message"]):
            msg = update.message
            if msg and msg.from_user:
                print(msg.from_user.id, msg.chat.id, msg.chat.type)
asyncio.run(run())
'
```

### Portainer

1. У терміналі на тому самому Docker-хості, яким керує Portainer, зберіть образ `docker build -t home-presence-bot:1 .`. Для віддаленого Docker-хоста образ має бути побудований на ньому або доступний йому через ваш реєстр.
2. Для нового NetAlertX створіть стек **Stacks → Add stack → Web editor**. Назва `home-presence-netalertx`. Вставте `docker-compose.netalertx.yml`, додайте лише змінені `NETALERTX_*` у **Environment variables** і натисніть **Deploy the stack**. Після цього завершіть налаштування сканера через UI NetAlertX.
3. Окремо створіть стек `home-presence`. Вставте `docker-compose.yml`, завантажте заповнений `.env` через **Load variables from .env file** і натисніть **Deploy the stack**. Образ будується зовні, тому стек підходить для локального й віддаленого Docker Standalone. [Створення стека в Portainer](https://docs.portainer.io/user/docker/stacks/add) · [Зовнішня збірка для віддаленого хоста](https://docs.portainer.io/faqs/known-issues/docker-compose-files-including-build-steps-fail)
4. Переконайтеся, що бот отримав статус healthy, а `/status` показує коректну відповідь NetAlertX та поступове оновлення часу сканування. Запити статусу виконуються в дозволеному приватному чаті або групі.

Запуск зі звичайного Compose на HP використовує той самий образ і том. Оберіть один спосіб запуску для кожного стека.

```bash
docker build -t home-presence-bot:1 .
docker compose -p home-presence config --quiet
docker compose -p home-presence up -d
docker compose -p home-presence ps
docker compose -p home-presence logs --tail=30 bot
```

Існуючі стеки Portainer, Beszel, Duplicati та інших сервісів не потрібні для розгортання. SQLite зберігається в іменованому томі `home_presence_db`, дані нового NetAlertX в `home_presence_netalertx`. Залиште томи під час повторного створення контейнерів. Для копії SQLite під час роботи використовуйте механізм SQLite backup, щоб включити дані WAL.

## 4. Перша реєстрація двох телефонів

1. Підключіть обидва телефони до основного Wi-Fi Tenda та перегляньте MAC саме для цієї мережі в налаштуваннях кожного телефона. Звірте адреси з NetAlertX.
2. Адміністратор відкриває `/unknown`, вибирає першу MAC та натискає **Категорія → Мій пристрій**. Якщо MAC ще не відображається, використайте `/devices → Додати за MAC`, потім відкрийте категорію.
3. Відповідайте на конкретний запит бота, наприклад `iPhone Ані`. У картці натисніть **Власник** і надішліть `Аня | 123456789` з фактичним Telegram user ID, який є в `MEMBER_USER_IDS`.
4. Увімкніть **Моніторинг** і **Ключі**. Кнопкою **Chat ID** можна явно вказати приватний чат власника або дозволену спільну групу. Для приватних повідомлень Ані можна залишити автоматичний маршрут. Звичайні сповіщення про прихід і вихід вмикаються окремо.
5. Повторіть для телефона адміністратора. Укажіть його ім’я і user ID з `ADMIN_USER_IDS`. За замовчуванням нагадування адміністратора надходить у маршрут **Адмін**.
6. Перевірте `/home` після двох свіжих сканів. Перший стан встановлюється тихо. Для перевірки повідомлення від'єднайте один телефон від Wi-Fi, дочекайтеся підтвердженого виходу та щонайменше 20 хвилин від першого негативного скану, після чого знову підключіть телефон і дочекайтеся двох свіжих позитивних сканів.

На старті бот імпортує історичний інвентар NetAlertX до `/unknown`. Для сповіщень про вже присутні MAC під час першого імпорту задайте `ANNOUNCE_INITIAL_DEVICES=true` до першого запуску. Наступні раніше невідомі MAC автоматично створюють картку з кнопками **Мій пристрій**, **Гість**, **Ігнорувати**, **Невідомий**. При класифікації гостя однакове ім’я зв'язує кілька його MAC з одним записом. Для двох різних гостей з однаковим ім’ям задайте різні підписи. Для зміни MAC відкрийте картку і натисніть **MAC**. Історія з попередньою адресою зберігається, колишня адреса потрапляє до ігнорованих.

## 5. Команди й повідомлення

| Команда | Дія |
| --- | --- |
| `/start` | Головне меню |
| `/home` | Підтверджені присутні пристрої та їхні власники |
| `/devices` | Зареєстровані та ігноровані MAC, картки й ручна реєстрація |
| `/guests` | Гості, їхні MAC за кількістю та стан присутності |
| `/unknown` | Пристрої, які ще можна класифікувати |
| `/history` | Історія появ і зникнень із пагінацією |
| `/settings` | Одержувачі, пороги й перехід до карток телефонів |
| `/status` | API, фактичний інтервал оновлень і стан доставки |
| `/help` | Довідка |
| `/cancel` | Скасування відкритих запитів введення в поточному чаті |

## 6. Контракт API та час виявлення

- Бот читає `GET /devices` на `GRAPHQL_PORT` з `Authorization: Bearer …`. У 26.10.28 запит без `limit` повертає всі записи в об’єкті `{"success": true, "devices": [...]}` одним читанням. Джерело істини для присутності — цілочислове поле `devPresentLastScan` зі значенням 0 або 1. У картці NetAlertX `devStatus` відображає похідні стани на кшталт `On-line`, `Off-line`, `Down` та `Sleeping`. `devLastConnection` у сирих REST-рядках записано в UTC. [REST Devices](https://docs.netalertx.com/API_DEVICES/) · [Поля бази](https://docs.netalertx.com/DATABASE/) · [Реалізація REST](https://github.com/netalertx/NetAlertX/blob/v26.10.28/server/api_server/api_server_start.py) · [Оновлення полів](https://github.com/netalertx/NetAlertX/blob/v26.10.28/server/scan/device_handling.py)
- `GET /events` читає журнал подій NetAlertX, включно з типом, MAC та часом. Події виникають при змінах і не підтверджують кожен цикл сканування. Бот записує власні підтверджені переходи. Відмітка `last_scan_run` у NetAlertX належить старту циклу планувальника. Для визначення підтверджень бот використовує `devLastConnection` контрольного пристрою, який ARPSCAN реально виявив. Цей підхід розрахований на спільний сегмент і один узгоджений цикл присутності. [Events API](https://docs.netalertx.com/API_EVENTS/) · [Основний цикл NetAlertX](https://github.com/netalertx/NetAlertX/blob/v26.10.28/server/__main__.py)
- Перший стан встановлюється після двох позитивних сканів або щонайменше п’яти хвилин послідовних негативних сканів. Для появи збігаються свіжі часові мітки телефона й контролю. Для зникнення потрібен явний негативний прапорець із попереднім часом виявлення. Порожня або помилкова відповідь, зниклий рядок, прострочені дані або відсутність контролю не перетворюються на вихід. Дубль часу пропускається. При розриві інтервалу або перезапуску накопичення доказів відновлюється зі свіжих сканів.
- Типова мінімальна відсутність для нагадування задається як 600 секунд, а окремий захист від повторів як 1200 секунд. Застосовується більше з двох значень. Час відсутності рахується від першого прийнятого негативного скану до першого позитивного в підтвердженій послідовності. Реальна затримка складається з розкладу сканування, його тривалості й опитування API. П’ять хвилин означають нижню межу, а рішення приймається на наступному придатному скані.
- SQLite записує стан, історію та чергу повідомлень однією транзакцією. Після підтвердженої відмови Telegram через обмеження швидкості черга повторює спробу. При обриві після можливого прийняття повідомлення доставка позначається невизначеною. Це дозволяє уникнути дубля ціною можливого пропуску. Нагадування в черзі мають термін 15 хвилин, сповіщення про нову MAC — добу. [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage)

## 7. iPhone та діагностика

- Для iOS 18+ на довіреному домашньому SSID з WPA2/WPA3 виберіть **Приватна адреса Wi‑Fi → Фіксована**. Реєструйте цю адресу в боті. У режимі **Змінювана** MAC може періодично оновлюватися. Після скидання мережевих налаштувань або забування мережі звірте адресу й за потреби змініть прив’язку. Приватну фіксовану адресу можна залишити ввімкненою. [Apple Support](https://support.apple.com/en-us/102509)
- iPhone у режимі сну може пропускати ARP-відповіді, особливо за частого сканування. Довгі розриви можливі через енергозбереження, гостьовий SSID, client isolation, VLAN або мережеві розширювачі. Якщо на хвилинному розкладі є стрибки, перевірте історію NetAlertX з заблокованим екраном і за потреби узгоджено збільшіть інтервал сканування та `SCAN_SECONDS`. Виявлення показує присутність телефона у Wi‑Fi. [Діагностика пропусків NetAlertX](https://docs.netalertx.com/FIX_OFFLINE_DETECTION/) · [Доступність сегментів](https://docs.netalertx.com/REMOTE_NETWORKS/)
- У разі `HTTP 401` або `403` перевірте токен і порт. При повідомленні про контрольну MAC перевірте, чи NetAlertX бачить Tenda у кожному циклі, і перегляньте розклад та логи ARPSCAN. Якщо інтервал циклів стабільно перевищує `MAX_SCAN_GAP_SECONDS`, вирівняйте конфігурацію бота з фактичною частотою. На великих мережах тривалість сканування залежить від CIDR та налаштувань ARPSCAN.
- На HP можна перевірити відповідь API з контейнера без друку токена. Команда показує лише часову мітку контрольного запису та розмір інвентарю.

```bash
docker compose -p home-presence exec -T bot python -c '
import asyncio, aiohttp
from config import Config
from netalertx_client import NetAlertXClient
async def check():
    c = Config.from_env()
    async with aiohttp.ClientSession() as session:
        snapshot = await NetAlertXClient(session, c.api_url, c.api_token, c.reference_mac, c.api_timeout).snapshot()
        print("Scan UTC epoch:", snapshot.scan_time, "Devices:", len(snapshot.devices))
asyncio.run(check())
'
```
